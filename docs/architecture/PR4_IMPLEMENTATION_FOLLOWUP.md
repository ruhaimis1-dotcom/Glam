## أذونات القراءة وRLS المقترحة

ينطبق هذا الجدول على القراءة المباشرة من الخدمات والتصنيفات والتصنيفات الفرعية والخيارات بعد تطبيق migration، ولم يُثبت تشغيليًا بعد.

| الهوية | القراءة المقصودة |
| --- | --- |
| مالكة/مديرة المؤسسة نفسها | كامل كتالوج مؤسستها، بما فيه غير النشط وغير المنشور |
| عميلة بلا عضوية أو زائرة | عناصر نشطة فقط لمؤسسة active ذات صفحة published، مع احترام نشاط التصنيف والأب |
| مختصة أو عضو في مؤسسة أخرى | نفس حدود القراءة العامة؛ لا يحصل على امتياز إدارة الكتالوج |
| service_role أو مالك قاعدة البيانات | خارج ضمانات RLS المعتادة؛ لا يستخدم كهوية لاختبار العميلة |

تمنح SELECT للجداول الأربعة إلى anon/authenticated، وتسحب أذونات الجدول الأخرى من PUBLIC/anon/authenticated. الكتابة تمر بالعقود المتحققة. يجب فحص أي منح أعمدة أو أدوار موروثة غير موثقة على النسخة الفعلية.

تُضاف سياسة permissive للقراءة المقصودة وسياسة restrictive مماثلة لكل جدول: الأخيرة تضع حدًا على سياسات السماح القديمة، دون حذفها أو تخمين أسمائها. أي سياسة restrictive موجودة قد تضيق القراءة أكثر. لا يمكن إعلان نجاح القراءة دون اختبار جميع السياسات معًا.

دالة الرؤية الخاصة SECURITY DEFINER تقرأ العضوية وحالة نشر المؤسسة دون منح العميلة أو الزائرة قراءة جداول العضوية والمؤسسات. تعيد boolean فقط، وتستمد الهوية من auth.uid(). يمنح لها EXECUTE للدورين، ولا يضاف anon USAGE على المخطط الخاص؛ مرجعها داخل السياسة يُحل أثناء إنشاء السياسة. هذا المسار واختبار الاستدعاء المباشر وامتيازات المالك يحتاجون تحققًا في PostgreSQL الحقيقي.

حالات المؤسسة pending/suspended لا تظهر في القراءة العامة. المالكة والمديرة تستطيعان إدارة كتالوجهما حتى في هذه الحالات؛ تغيير هذه القاعدة يحتاج قرارًا منتجيًا. إخفاء التصنيف غير النشط يخفي خدماته العامة أيضًا. هذه تغييرات سلوكية ينبغي اختبارها وقبولها.

**حد مهم:** هذه السياسات لا تعيد كتابة المواعيد أو الحجوزات السابقة، ولا تضبط تلقائيًا دوال SECURITY DEFINER القديمة أو جدول delivery options. يجب فحص RPCs مثل `glam_salon_page`, `glam_salon_slots`, `glam_available_appointments` ومسارات الحجز المباشر بحثًا عن قراءة أو حجز خدمة معطلة. لا تدعي هذه المتابعة إغلاق كل مسارات القراءة أو منع الحجز القديم على مستوى الخادم.

## المخاطر المتبقية وبوابة التطبيق

1. أخذ نسخة baseline فعلية ومراجعة ACL والسياسات والدوال الحالية وسلامة البيانات. فحوص البيانات داخل migration لم تُنفذ هنا.
2. مراجعة خطة التطبيق والقفل والنسخ الاحتياطي والرجوع. إضافة القيود تفحص البيانات وتأخذ أقفالًا؛ حدود المهلة توقفها ولا تثبت أنها ملائمة للإنتاج.
3. تطبيق النسخة المراجعة على الاختبار فقط بعد الإذن، ثم تشغيل script واختبارات REST بحسابات حقيقية عبر publishable key، لا service_role.
4. التحقق من تضمين التصنيف والخيارات في REST بعد تغيّر FK/cache، والواجهة RTL، والتحميل والفشل وزر إعادة المحاولة، وتبديل الصالون والجلسة.
5. اختبار حقيقي متزامن لسحب العضوية وحذف التصنيفات والحفظ. لا يوجد optimistic concurrency/expected revision أو مفتاح idempotency؛ قد يطمس حفظ متأخر تعديلًا سابقًا أو يتكرر الإنشاء بعد فقد الرد.
6. اختبار الخدمات المرتبطة بحجوزات وتعيينات مختصات، وRPCs القديمة والظهور العام بعد التعطيل. لا يختبر script الحالي كل سلوك FK المرتبط بالحجوزات ولا الأداء والتزامن.
7. ما زال جلب المواعيد يحدد الصالون بالاسم المأخوذ من نموذج العرض الحالي؛ الأسماء غير الفريدة واستبدالها بربط organization_id موثوق خطر سابق يحتاج متابعة مستقلة. إنشاء خدمة لا ينشئ مواعيد أو يضمن ظهورها في صفحة الحجز.
8. SQL مُعد وفق الأعمدة المؤكدة، لكنه لم يُنفذ أو يُثبت نحويًا وتشغيليًا داخل PostgreSQL. تبقى الموافقة على التطبيق والدمج والنشر منفصلة بعد عرض نتائج الاختبار.
