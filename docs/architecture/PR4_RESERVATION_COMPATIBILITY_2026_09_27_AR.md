# PR #4 — قنوات الحجز والتوافق والتزامن

الفرع: `agent-os/p1.2-business-operations`، نقطة البدء `98b955668334f924c93eed639e837e4f75a513e0`.

المشكلة: دوال GLAM الأصلية `reserve` و`reserve_direct` و`reschedule` لا تمرر قناة، بينما ترحيل القنوات السابق يشترطها. كذلك يجب أن تخضع الكتابة المباشرة من واجهة العميلة للتحقق المتزامن نفسه الذي تستخدمه RPC. التغيير الجديد يحافظ على التواقيع المنشورة ويضيف overloads بقناة صريحة، ويقفل البيانات ذات الصلة قبل قبول الحجز.

النتيجة: **55 ترحيلًا حيًا**، أحدثها `20260923214630`. الترحيلات الثلاثة السابقة لـPR غير مطبقة على GLAM. أُنشئ الترحيل الرابع بعد المقارنة. [دليل الأرقام وبصمات الملفات](evidence/PR4_2026_09_27_migration_order.json) لا يحتوي اعتمادًا أو بيانات عملاء.

## عقد التوافق

| الطلب | السلوك |
|---|---|
| reserve/reserve_direct مع p_channel | تحقق القناة المفعلة والسعر/المدة عند الإدراج؛ حفظ القناة في الحجز |
| التوقيع القديم بلا قناة | اختيار القناة الوحيدة المفعلة فقط؛ لا اختيار تخميني عند وجود قناتين أو عدم إعداد القنوات |
| reschedule بلا p_channel | الحفاظ على قناة الحجز الأصلي؛ رفض العملية إذا عُطلت بدل التحويل الصامت لقناة أخرى |
| reschedule بقناة صريحة | السماح بقناة صالحة للخدمة نفسها؛ إنشاء بديل مع replaces_reservation_id وbooking_source |
| حجز تاريخي delivery_channel=NULL | إبقاء السجل القديم كما هو؛ اختيار صريح للبديل عند الغموض؛ رفض ملئه عبر تحديث الحالة فقط |
| تكرار request_id | نفس النتيجة إذا تطابقت هوية الطلب؛ REQUEST_MISMATCH عند تغيير الموعد أو القناة |
| فشل البديل | تراجع إلغاء الأصل داخل المعاملة؛ يبقى الحجز الأصلي مؤكدًا |

التواقيع القديمة ليست overloads ذات defaults، فلا يلتبس اختيار PostgREST بين الطلب القديم والجديد. ACL القديمة محفوظة، والجديدة EXECUTE لـauthenticated فقط. دوال القفل والتحقق الداخلية لا تُمنح للعميلة أو الزائرة. كل هوية تُستمد من auth.uid، وإعادة الجدولة مقيدة بصاحبة الحجز.

## التزامن وتغيّر الإعداد

المسار المباشر الحالي للعميلة (REST INSERT مع delivery_channel) محفوظ واختُبر عبر المتصفح. يسبق محفز `glam_00_booking_concurrency` بقية محفزات INSERT. يقفل هوية الطلب ثم المختصة قبل قراءة التداخل، ويقفل الموعد والمؤسسة والخدمة والتصنيفات. تتحقق قناة التقديم بقفل صفها، ويعيد الحجز فحص revision بعد انتظار تعديل الخدمة. نفس حراس الإدراج يحمون RPC.

اختبارات جلسات مستقلة تحققت من: طلبين متطابقين بالتزامن، request_id واحد لموعدين مختلفين، حجزَي REST لموعدين متداخلين، تنافس RPC مع REST، إعادة جدولة متزامنة، تعديل القناة أولًا ثم الحجز، الحجز أولًا ثم تعطيل القناة، وتغيير السعر الذي يجعل revision الموعد قديمًا.

يعتمد التحقق بعد القفل على snapshot جديدة في READ COMMITTED، وهو إعداد PostgREST المختبر. الكتابة بمستوى snapshot ثابت تُرفض بـ`BOOKING_ISOLATION_UNSUPPORTED` بدل السماح بقراءة تداخل قديمة. هذا قيد صريح يجب الحفاظ عليه لدى أي مستهلك SQL جديد.

## الحدود والقرارات المنتَجية

- التوافق التوقيعي محفوظ. لا يمكن استنتاج اختيار عميلة قديمة بين الصالون والمنزل من طلب لا يحمل قناة؛ `DELIVERY_REQUIRED` قرار آمن موثق يحتاج قبول المنتج قبل الإطلاق. واجهة PR الحالية ترسل قناة صريحة.
- الخدمات القديمة بلا قنوات تحتاج قرار المالكة/المديرة، دون backfill تخميني. لا تغيير تلقائي للسعر أو المدة أو رسوم الانتقال. مسار التسعير المتقدم وعنوان الزيارة المنزلية خارج هذه الشريحة.
- السجل القديم محفوظ؛ الاختبارات الخاصة بتاريخ NULL تُنشئ fixture محلية، ولا تعدّل بيانات GLAM الحية.
- اسم/هوية صفحة الصالون في الواجهة ما زالا من الدليل الثابت المعروف، بينما الخدمة والحجز من القاعدة. أجهزة فعلية وSafari وOAuth والحمل واسع النطاق خارج الأدلة الحالية.

## خطة التطبيق والتراجع

قبل أي تطبيق حي: موافقة بشرية، فحص drift وسجل الترحيلات مجددًا، مراجعة الخدمات غير المهيأة للقنوات، نسخة احتياطية مع تجربة استعادة، ونافذة صيانة توقف كتابات الحجز أثناء تطبيق الترحيلات الأربعة والتحقق منها. لا تُفتح الكتابة بين الترحيل الثالث والرابع. لا تُصلح ledger لتوهم أن التاريخ المفقود طُبق من الملفات المحلية.

كل ملف داخل معاملة مع lock_timeout=5s وstatement_timeout=60s. فشل الملف يتراجع عن ملفه فقط، وقد تبقى الملفات السابقة مكتملة. عند الفشل تبقى نافذة الصيانة حتى إكمال الإصلاح أو تنفيذ خطة تعويض معتمدة.

بعد COMMIT، إسقاط عمود القناة يفقد معلومات الحجوزات الجديدة، والرجوع إلى الترحيل الثالث يعيد مانع RPC القديم ويفقد حماية التزامن الجديدة. لذلك خطة الإصدار تحتاج ترحيلًا تعويضيًا يحافظ على البيانات والعقد أو إصلاحًا أماميًا مختبرًا؛ لا يوجد في هذا PR سكربت تراجع حي مُعتمد أو تجربة استعادة إنتاج. هذا شرط إطلاق متبقٍ، وليس اختبارًا ناجحًا مدعى.
