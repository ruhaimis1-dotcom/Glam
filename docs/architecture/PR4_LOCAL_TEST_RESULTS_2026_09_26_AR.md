## تغطية SQL الناجحة

المدخل هو [catalog_contract.sql](../../supabase/tests/catalog_contract.sql)، ويضم عبر `\ir` ملفي الحجز وقنوات التقديم. الحسابات صفوف اختبار جديدة في auth.users، ثم تعمل الاختبارات بـ`SET ROLE authenticated/anon` وclaim المستخدم، ولا تعتمد على تجاوز postgres لـRLS في assertions الخاصة بالمستخدمين.

- إنشاء الخدمة وقراءتها وتعديلها وحذفها بصلاحيات owner/manager، السعر الصفري، ثبات ID، revision عند التغيير وعدم تغييره عند no-op.
- CRUD للتصنيفات والأبناء، منع حذف المستخدم منها، ورفض organization/target/category مزور أو أب غير مطابق، وقيود FK المركبة حتى للكاتب الإداري.
- رفض العميلة والمختصة والزائرة ومسار العضوية المسحوبة في حالات الاختبار، ورفض الكتابة المباشرة، وفحص ACL للدوال العامة والخاصة.
- إخفاء غير المنشور وغير النشط، وتعطيل الرئيسي والفرعي كل على حدة مع استمرار نشاط الخدمة، وعودة القراءة بعد إعادة التفعيل؛ owner/manager يحتفظان بقراءة كتالوجهما.
- العميلة والزائرة: دوال الصالون والمواعيد وقراءة جدول المواعيد تحترم تعطيل التصنيف. إنشاء الحجز تحت authenticated يُرفض بـ`SERVICE_UNAVAILABLE`؛ تنجح حالة الموعد الصالح، وتتراجع حجوزات probes بعد اختبارها.
- استمرار قراءة الحجز السابق بعد التعطيل وجدول المديرة، وعدم إتاحة موعد ذي service_revision قديم عبر RPC وعدم السماح بحجزه.
- قنوات `salon/home` تقبل fixtures المحلية، والقناة غير المعروفة تُرفض، وحذف الخدمة يحذف خيارات التقديم المرتبطة. جميع الأدوار المختبرة، بما فيها owner/manager، ترفض SELECT/INSERT/UPDATE/DELETE المباشر على delivery options وفق grants الحالية.

**حد قنوات التقديم:** نجاح اختبار الرفض لا يعني أن واجهة إدارة القنوات تعمل. المخطط الحالي لا يمنح API roles تلك العمليات، وهذه الشريحة لا تضيف RPC لإدارتها. إذا كان CRUD لقنوات التقديم شرط اعتماد PR، فيلزم عقد وواجهة وmigration واختبارات مستقلة؛ لم نوسّع الصلاحيات لتجاوز ذلك.

## بوابة Auth/REST الدقيقة قبل الدمج

هذه اختبارات HTTP فعلية **على stack محلي كامل مطابق أو بيئة staging معتمدة**، وليست إذنًا لكتابة بيانات اختبار على مشروع GLAM الحي. لم تُنفذ في هذه المراجعة:

1. إنشاء حسابات owner A وmanager A وowner B وspecialist وcustomer في Auth وتسجيل دخول كل منها عبر `/auth/v1/token?grant_type=password`، واستخدام access JWT وpublishable/anon key في طلبات التطبيق؛ لا service_role في assertions. اختبار refresh token، وتسجيل الخروج وتبديل الحساب والمؤسسة ومسح حالة الواجهة. إثبات رفض JWT مفقود/غير صالح/منتهي للعمليات المحمية مع استمرار القراءة العامة المسموحة.
2. عبر `/rest/v1/rpc/glam_save_catalog_service` و`glam_delete_catalog_service` و`glam_save_catalog_category` و`glam_delete_catalog_category`: نجاح owner/manager داخل A، واستمرار النتائج بعد reload، ورفض المختصة والعميلة والزائرة والمؤسسة/ID المزورين. سحب عضوية manager ثم إعادة الطلب **بنفس JWT القديم** للتأكد أن فحص العضوية الحي يمنع العملية دون الاعتماد على refresh. التحقق من ثبات البيانات بعد كل رفض، لا الاكتفاء بكود HTTP.
3. قراءة `glam_services` والتصنيفات والتصنيفات الفرعية وvariants عبر REST بنفس select/embedding الذي يرسله التطبيق، وفحص عدم وجود خطأ علاقة ملتبسة بعد إضافة FK المركبة أو schema-cache قديم. إثبات عدم تسرب كتالوج B الخاص، مع السماح بكتالوجه العام المنشور وفق العقد.
4. تعطيل الرئيسي والفرعي كلٍّ على حدة مع بقاء الخدمة نشطة: قراءة REST وRPCs `glam_salon_page` و`glam_salon_slots` و`glam_available_appointments` وإدراج `/rest/v1/glam_reservations` تلتزم بالمنع. إعادة التفعيل تعيد المسارات الصحيحة؛ revision القديم يظل غير قابل للحجز؛ الحجز التاريخي وجدول الطاقم يظلان قابلين للقراءة. تُنشأ fixtures التعطيل إداريًا في بيئة الاختبار فقط لأن API لا يقدم تعديل active للتصنيف في هذه الشريحة.
5. اختبار أخطاء permission/network وretry في الواجهة بعد HTTP حقيقي: لا fallback لبيانات وهمية ولا نجاح قبل اكتمال إعادة القراءة، مع RTL لسطح المكتب والهاتف وتبديل الجلسة أثناء طلب جارٍ. التحقق أن `glam_private` ليس ضمن مخططات PostgREST المكشوفة؛ وإعادة اختبار رفض REST لقنوات التقديم لجميع الأدوار ما لم يُعتمد عقد مستقل لإدارتها.

نجاح SQL وQuality Gate لا يغني عن البنود أعلاه. تبقى كذلك اختبارات التزامن ومراجعة نطاق قنوات التقديم وخطة تطبيق migrations المذكورة سابقًا.
