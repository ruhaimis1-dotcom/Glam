- قاعدة البيانات وAuth وREST على شبكة Docker داخلية، بلا منافذ منشورة. Kong وحده على منفذ عشوائي مربوط بـ`127.0.0.1`، مع مساري `/auth/v1` و`/rest/v1` والتحقق من API key. المخطط المكشوف لـREST هو `public` فقط.
- لا اتصال بمشروع GLAM الحي، ولا قراءة اعتماداته، ولا `db push`. التصدير السابق schema-only تحت `supabase/.temp`، وSHA-256 المثبت هو `390756903381b1e8da2dcee4ab5b6cf9bcd32419e2d424c601b4a0d2b525d91e`.

- يبدأ GoTrue مخطط Auth التشغيلي بترحيلاته الرسمية. التصدير بلا بيانات لا يحتوي سجل `auth.schema_migrations`، لذلك لم نفبرك السجل ولم ندّعِ مطابقة إعدادات Auth المستضافة. مطابقة مخطط تطبيق GLAM ودوال JWT وروابط المستخدمين مفحوصة؛ إصدار Auth وإعدادات البريد والتأكيد المحلية محددة للاختبار.

3. رفض إنشاء/تعديل/حذف الخدمة وتعديل التصنيف للمختصة والعميلة والزائرة ومالكة الصالون الآخر. رفض الكتابة المباشرة على الجدول حتى للمالكة والمديرة، ومنع ID خدمة أو تصنيف تابع لمؤسسة أخرى، والتحقق أن الرفض لم يغيّر البيانات.
4. عدم تسرب كتالوج B غير المنشور للأدوار الأخرى؛ الخدمة العامة المقصودة متاحة للعميلة والزائرة. رفض repository الوصول الإداري إلى مؤسسة أخرى. سحب عضوية المديرة منع RPC وrepository **بنفس JWT القديم**.
5. نجاح علاقات REST المستخدمة حرفيًا في booking repository، بما فيها أسماء FK الصريحة بعد إضافة القيود المركبة. نجح `loadBookingCatalog` الفعلي، ولم تظهر مشكلة schema cache أو علاقة ملتبسة في البيئة المختبرة.
6. تعطيل الرئيسي والفرعي كل على حدة، مع بقاء الخدمة نشطة: إخفاء الخدمة والتصنيف عن العميلة، وإخفاء الفرعي النشط حين يتعطل أبوه، مع بقاء القراءة الإدارية. تحقق المسار الفعلي للحجز و`glam_salon_page` و`glam_salon_slots` و`glam_available_appointments` عبر HTTP للعميلة/الزائرة. رفض إدراج الحجز المباشر بـ`SERVICE_UNAVAILABLE`؛ إعادة التفعيل أعادت المسارات الصحيحة.
7. نجاح الحجز الحقيقي للعميلة عبر REST بعد تحديث revision المحلي للموعد؛ رفض revision قديم والحجز المكرر؛ بقاء سجل حجز العميلة وجدول الطاقم بعد تعطيل التصنيف. رفض مدة غير صالحة وحذف تصنيف مرتبط بخدمة.
8. عدم كشف `glam_private` عبر REST، ورفض GET/POST/PATCH/DELETE لقنوات التقديم لكل الأدوار الستة وفق عقد الصلاحيات الحالي. هذا إثبات للرفض، وليس تنفيذًا لميزة إدارة القنوات.

## إصلاحات إعداد الاختبار

- الانتظار لصحة PostgreSQL بعد انتهاء تهيئة الصورة، بدل التقاط خادم التهيئة المؤقت الذي يعاد تشغيله.
- استخدام قاعدة التشغيل الموجودة داخل الحاوية الجديدة، بدل نسخ قاعدة قالب عليها اتصالات.
- إضافة Kong بمنفذ loopback؛ الخدمات الخلفية تبقى داخل الشبكة الداخلية التي لا تنشر منافذها.
- إعادة منحة `PUBLIC USAGE` لمخطط public كما في المرجع بعد إعادة إنشائه: pg_dump يفترض وجود منحة bootstrap، لكن إنشاء schema بعد إسقاطه لا يعيدها. تقارن الأداة ACL الفعلية مستقلة عن فرق تمثيل pg_dump، وترفض أي اختلاف متبقٍ.
- توقفت إحدى المحاولات من 20:44 UTC إلى 07:26 UTC في اليوم التالي، ثم أعادت HTTP 401 في طلب كان يتوقع رفض FK؛ تجاوز ذلك عمر JWT المحدد بساعة. الإعادة الكاملة بجلسات جديدة نجحت؛ لم نخفّض شرط الاختبار أو نمدد عمر الرموز لإخفاء الحالة.

## ما بقي قبل الدمج

- **اختبار واجهة متصفح مرئية**: لم تُشغّل واجهة RTL للهاتف/سطح المكتب، أو تبديل الحساب أثناء طلب جارٍ، أو عرض أخطاء الشبكة/retry في المكونات. اختُبرت repositories الفعلية عبر HTTP، لا rendering أو تفاعل المتصفح.
- **التزامن والأداء**: لم يُختبر سباق جلسات متزامنة للحجز مع تعطيل التصنيف أو سحب العضوية، ولا اختبار حمل. التسلسل الناجح لا يثبت خلو السباق.
- **Auth المستضاف**: لم تُختبر إعدادات GLAM الحية أو البريد الخارجي/OTP/OAuth/إعادة تعيين كلمة المرور؛ الاختبار محلي بحسابات password مؤكدة. logout يبطل refresh، ولا نفترض إبطال access JWT فورًا قبل انتهاء صلاحيته.
- **نطاق المنتج والترحيلات**: إدارة قنوات التقديم ما زالت تحتاج عقدًا مستقلًا إن كانت شرط دمج. يلزم اعتماد خطة تطبيق/تراجع الترحيلتين ومراجعة مسارات مثل إلغاء نشر الصالون/تعليق المؤسسة خارج سيناريو التصنيفات؛ لا تزال migrations ليست bootstrap كاملًا للإنتاج.

يبقى PR مسودة. لا دمج أو نشر أو SQL على GLAM الحي.
